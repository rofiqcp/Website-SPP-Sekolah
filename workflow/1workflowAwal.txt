Berikut rancangan **sistem keuangan terpadu Yayasan Pendidikan El Yaomy Klaten** berbasis **PostgreSQL**, siap untuk ribuan user, aman secara cybersecurity, dan modular. Saya anggap sistem ini dipakai oleh **admin yayasan, bendahara sekolah, kepala sekolah, wali kelas, guru/pegawai, siswa, orang tua/wali, kasir, petugas kantin, petugas gudang, dan auditor**.

Riset fitur umum saya ambil dari pola aplikasi keuangan sekolah/pesantren yang umum di Indonesia: tagihan/SPP, pembayaran otomatis, VA/QRIS, tabungan digital, PPDB, e-kantin, POS/kasir, kartu siswa, notifikasi WhatsApp, serta laporan otomatis. Beberapa platform lokal juga menonjolkan integrasi pembayaran SPP, VA, e-kantin/e-mart, tabungan, dan cashless siswa. ([School Payment App][1]) Untuk keamanan, desain ini mengikuti prinsip OWASP ASVS/API Security: autentikasi kuat, kontrol akses per objek, validasi input, logging, kriptografi, session security, dan perlindungan data pribadi. ([OWASP][2]) Untuk pembayaran Indonesia, integrasi sebaiknya mengikuti pola payment gateway/VA/QRIS dan standar Open API pembayaran seperti SNAP yang diarahkan untuk interoperabilitas dan infrastruktur pembayaran yang aman/reliable. ([Bank Indonesia][3])

1. Tabungan siswa pribadi

```text

    validasi amount > 0
    mulai database transaction

        buat ledger_entry kredit ke akun tabungan siswa
        buat ledger_entry debit ke kas/bank
        update cached_balance
        buat audit_log
    commit
    cetak/kirim bukti setor
```

9. Refund
10. Void/cancel payment
11. Bukti bayar PDF/WhatsApp
12. Auto-posting jurnal
13. Dashboard pembayaran realtime

Alur payment gateway:

```text
CREATE_ONLINE_PAYMENT(parent_id, invoice_ids, method):
    validasi invoice milik anak dari parent_id
    hitung total unpaid
    buat payment_intent status=pending
    request VA/QRIS/payment_url ke gateway
    simpan external_reference
    kembalikan instruksi pembayaran ke frontend
```

Webhook:

```text
PAYMENT_WEBHOOK(payload, signature):
    verifikasi signature
    cek idempotency external_transaction_id
    jika sudah diproses:
        return success
    mulai database transaction
        cari payment_intent
        validasi amount cocok
        ubah status payment_intent = paid
        buat payment
        alokasikan pembayaran ke invoice_items
        update invoice status
        buat jurnal:
            debit bank/payment clearing
            kredit piutang siswa / pendapatan diterima dimuka / pendapatan
        buat audit_log
    commit
    kirim notifikasi bukti bayar
```

Catatan keamanan pembayaran:

* Jangan percaya status pembayaran dari frontend.
* Status sah hanya dari callback gateway atau hasil inquiry resmi.
* Callback harus pakai signature/HMAC.
* Wajib idempotent.
* Nominal harus dicocokkan.
* Rekening tujuan harus milik yayasan/unit.

## G. Jurnal

Jurnal adalah inti akuntansi.

Fitur:

1. Chart of Accounts / COA
2. Jurnal otomatis dari transaksi
3. Jurnal manual
4. Jurnal penyesuaian
5. Jurnal pembalik
6. Jurnal penyusutan
7. Jurnal koreksi
8. Approval jurnal manual
9. Posting/unposting
10. Lock periode
11. Lampiran bukti
12. Audit jurnal

Aturan:

* Total debit harus sama dengan total kredit.
* Jurnal yang sudah posted tidak boleh diedit.
* Koreksi menggunakan reversal.
* Jurnal otomatis harus menyimpan source module dan source transaction ID.

Contoh jurnal:

Pembayaran SPP tunai:

```text
Debit  Kas Sekolah                 500.000
Kredit Piutang SPP                 500.000
```

Generate tagihan SPP:

```text
Debit  Piutang SPP                 500.000
Kredit Pendapatan SPP              500.000
```

Atau bila sekolah memakai basis kas, pendapatan diakui saat bayar. Pilihan basis akuntansi harus ditentukan sejak awal.

Pseudo-validasi jurnal:

```text
POST_JOURNAL(journal_id):
    ambil semua journal_lines
    total_debit = sum(debit)
    total_credit = sum(credit)
    jika total_debit != total_credit:
        reject
    jika period locked:
        reject
    set status = posted
    update general ledger
```

# 4. Desain PostgreSQL

## 4.1 Prinsip Desain Database

Untuk Yayasan El Yaomy, saya sarankan:

**Single PostgreSQL cluster, shared schema, semua tabel punya `tenant_id` / `foundation_id` / `unit_id`, ditambah Row Level Security untuk proteksi data.**

Alasannya:

* Lebih mudah dikembangkan untuk satu yayasan dengan banyak unit.
* Tetap bisa konsolidasi laporan.
* Lebih mudah backup.
* Bisa ditingkatkan ke partitioning saat data besar.
* Multi-tenant model dengan shared tables memang umum, tetapi harus disiplin memakai tenant key dan proteksi query; alternatifnya schema-per-tenant lebih terisolasi tetapi migrasi lebih rumit. ([MonPG][6])

Gunakan:

* UUID primary key
* `created_at`, `updated_at`, `deleted_at`
* `created_by`, `updated_by`
* Soft delete untuk master data
* Hard delete hanya untuk data sementara
* Audit log untuk semua aksi penting
* Financial transaction harus append-only
* Money pakai `BIGINT` dalam rupiah, bukan float
* Gunakan `NUMERIC(18,2)` hanya jika butuh desimal
* Index semua foreign key
* Partial index untuk status aktif/pending
* Partition untuk tabel transaksi besar

# 14. Cybersecurity Design

## A. Autentikasi

1. Password hash pakai Argon2id/bcrypt.
2. MFA untuk admin, bendahara, kepala sekolah.
3. OTP untuk orang tua.
4. Rate limit login.
5. Lock akun setelah percobaan gagal.
6. Session timeout.
7. Refresh token rotation.
8. Re-authentication untuk aksi sensitif seperti refund, ubah rekening, void transaksi, approval besar. OWASP menyarankan autentikasi ulang untuk aktivitas mencurigakan, pemulihan akun, dan aksi kritis. ([OWASP Cheat Sheet Series][8])

Pseudo:

```text
LOGIN(identifier, password):
    cek rate limit by IP + identifier
    ambil user
    jika user locked:
        reject
    verify password hash
    jika gagal:
        increment failed_login
        log attempt
        reject
    jika MFA aktif:
        buat mfa_challenge
        return need_mfa
    buat access_token pendek
    buat refresh_token rotating
    log success
```

## B. Authorization

1. RBAC: role-based.
2. ABAC: cek unit, kelas, siswa, pemilik akun.
3. Object-level permission di setiap endpoint.
4. Policy engine internal.

Pseudo:

```text
AUTHORIZE(user, action, resource):
    cek permission action pada role user
    cek scope:
        jika resource.unit_id bukan dalam user.allowed_units:
            reject
        jika user role parent:
            pastikan resource.student_id milik anak user
        jika user role wali_kelas:
            pastikan student.class_id == user.class_id
    allow
```

## C. API Security

1. Semua API pakai HTTPS.
2. Input validation.
3. Output encoding.
4. CSRF protection untuk cookie session.
5. CORS ketat.
6. Rate limit per user/IP/device.
7. Idempotency key untuk transaksi.
8. Request ID untuk tracing.
9. Tidak expose incremental ID.
10. Gunakan UUID.
11. Pagination wajib.
12. File upload dibatasi MIME, ukuran, antivirus scan.
13. Webhook signature verification.
14. API inventory terdokumentasi.

OWASP API Security Top 10 2023 menempatkan Broken Object Level Authorization sebagai risiko utama API, sehingga semua endpoint seperti `/students/{id}`, `/invoices/{id}`, `/wallets/{id}` harus cek kepemilikan dan scope, bukan sekadar login. ([OWASP][4])

## D. Data Protection

1. Enkripsi at-rest untuk database/disk.
2. Enkripsi field sensitif:

   * nomor identitas
   * nomor rekening
   * token payment gateway
3. Masking data di UI:

   * nomor HP
   * rekening
   * NIK bila ada
4. Backup terenkripsi.
5. Least privilege database user.
6. Data retention policy.
7. Audit siapa melihat/mengubah data.
8. Jangan simpan password, PIN, OTP plain text.
9. Jangan simpan data kartu pembayaran.

## E. Audit & Anti-Fraud

Transaksi yang harus masuk audit:

1. Login admin
2. Generate tagihan
3. Ubah nominal tagihan
4. Diskon/beasiswa
5. Pembayaran
6. Void/refund
7. Tarik tabungan
8. Ubah saldo
9. Posting jurnal
10. Hapus/ubah aset
11. Ubah role user
12. Export data siswa
13. Ubah konfigurasi payment gateway

Anti-fraud rule:

```text
DETECT_SUSPICIOUS_TRANSACTION(transaction):
    jika void/refund berulang oleh kasir sama:
        flag
    jika diskon besar tanpa approval:
        flag
    jika tarik tabungan di atas limit:
        require approval
    jika transaksi terjadi di luar jam operasional:
```

# 16. Pseudo-code Modul Utama

## 16.1 Generate Invoice

```text
FUNCTION generate_invoice_for_student(student, billing_rule, period):
    IF invoice_exists(student.id, billing_rule.id, period):
        RETURN existing_invoice

    base_amount = billing_rule.amount
    discount = calculate_discount(student, billing_rule)
    penalty = 0
    total = base_amount - discount + penalty

    invoice = create_invoice(
        student_id = student.id,
        due_date = calculate_due_date(billing_rule, period),
        total_amount = total,
        status = "published"
    )

    create_invoice_item(
        invoice_id = invoice.id,
        billing_type_id = billing_rule.billing_type_id,
        amount = base_amount,
        discount_amount = discount,
        net_amount = total
    )

    IF accounting_policy == "accrual":
        create_journal_for_invoice(invoice)

    send_invoice_notification(student.guardian)

    RETURN invoice
```

## 16.2 Payment Allocation

```text
FUNCTION allocate_payment(payment, invoice_list):
    remaining = payment.amount

    FOR invoice IN sort_by_due_date(invoice_list):
        unpaid = invoice.outstanding_amount

        allocation_amount = MIN(remaining, unpaid)

        create_payment_allocation(payment.id, invoice.id, allocation_amount)

        invoice.paid_amount += allocation_amount
        invoice.outstanding_amount -= allocation_amount

        IF invoice.outstanding_amount == 0:
            invoice.status = "paid"
        ELSE:
            invoice.status = "partial"

        remaining -= allocation_amount

        IF remaining == 0:
            BREAK

    IF remaining > 0:
        create_credit_balance(payment.student_id, remaining)
```

## 16.3 Jurnal Pembayaran

```text
FUNCTION create_journal_for_payment(payment):
    journal = create_journal_entry(
        date = payment.paid_at,
        source_module = "payment",
        source_id = payment.id
    )

    debit_account = resolve_cash_or_bank_account(payment.method)
    credit_account = resolve_receivable_account(payment)

    add_journal_line(journal, debit_account, debit = payment.amount)
    add_journal_line(journal, credit_account, credit = payment.amount)

    validate_debit_credit_balance(journal)

    post_journal(journal)
```

## 16.4 Top-up Dompet

```text
FUNCTION topup_wallet(wallet_id, amount, method, actor):
    authorize(actor, "wallet.topup", wallet_id)

    IF amount <= 0:
        REJECT

    BEGIN_TRANSACTION
        wallet = lock_wallet(wallet_id)

        transaction = create_wallet_transaction(
            wallet_id = wallet.id,
            type = "topup",
            amount = amount
        )

        create_wallet_ledger(
            wallet_id = wallet.id,
            direction = "credit",
            amount = amount,
            balance_after = wallet.balance + amount
        )

        wallet.balance += amount

        create_journal_wallet_topup(transaction)

        audit(actor, "wallet.topup", wallet_id)
    COMMIT
```

## 16.5 Checkout E-Kantin

```text
FUNCTION canteen_checkout(student_id, cart, cashier):
    authorize(cashier, "canteen.checkout", cashier.unit_id)

    student = get_student(student_id)
    wallet = lock_wallet(student.wallet_id)

    total = calculate_cart_total(cart)

    IF total > wallet.balance:
        REJECT "Saldo tidak cukup"

    IF exceeds_daily_limit(student_id, total):
        REJECT "Melebihi limit harian"

    BEGIN_TRANSACTION
        order = create_canteen_order(student, cashier, total)

        FOR item IN cart:
            validate_stock(item.product_id, item.qty)
            create_order_item(order.id, item)
            decrease_stock(item.product_id, item.qty)

        debit_wallet(wallet, total, source = order)

        create_journal_canteen_sale(order)

        audit(cashier, "canteen.checkout", order.id)
    COMMIT

    notify_guardian(student.guardian, order)
```

```text
FUNCTION void_transaction(transaction_id, actor, reason):
    authorize(actor, "transaction.void", transaction_id)

    IF transaction.status != "success":
        REJECT

    IF actor.role not allowed OR amount > actor.void_limit:
        require_approval()

    BEGIN_TRANSACTION
        original = lock_transaction(transaction_id)

        create_reversal_transaction(original, reason)
        create_reversal_journal(original.journal_id)
        restore_invoice_or_wallet_or_stock(original)

        original.status = "voided"

        audit(actor, "transaction.void", transaction_id)
    COMMIT
```

## 16.7 Closing Kasir

```text
FUNCTION close_cashier_session(session_id, actual_cash, actor):
    session = get_active_session(session_id)

    authorize(actor, "cashier.close", session)

    system_cash = calculate_cash_in_session(session)

    difference = actual_cash - system_cash

    BEGIN_TRANSACTION
        session.closing_cash_actual = actual_cash
        session.closing_cash_system = system_cash
        session.difference_amount = difference
        session.status = "closed"
        session.closed_at = now()

        IF difference != 0:
            create_cash_difference_record(session, difference)

        audit(actor, "cashier.close", session.id)
    COMMIT
```

```text
FUNCTION balance_sheet(unit_id, as_of_date):
    authorize(current_user, "report.balance_sheet", unit_id)

    balances = get_account_balances(unit_id, as_of_date)

    assets = sum_account_type(balances, "asset")
    liabilities = sum_account_type(balances, "liability")
    equity = sum_account_type(balances, "equity")
    surplus_deficit = calculate_current_year_result(unit_id, as_of_date)

    total_right_side = liabilities + equity + surplus_deficit

    IF assets != total_right_side:
        mark_report_as_unbalanced()

    RETURN report
```

# 20. Kesimpulan Desain

Untuk kebutuhan Yayasan Pendidikan El Yaomy Klaten, sistem idealnya dibuat sebagai **platform keuangan sekolah terpadu**, bukan hanya aplikasi SPP. Intinya:

1. **Tagihan, pembayaran, tabungan, dompet, kantin, kasir, inventaris, aset, jurnal, neraca, laporan, dan RAB harus terhubung.**
2. **Semua transaksi uang harus masuk ledger dan jurnal.**
3. **Saldo siswa/dompet/tabungan harus immutable ledger, bukan angka manual.**
4. **Payment online wajib idempotent, signed webhook, dan rekonsiliasi.**
5. **PostgreSQL harus didesain dengan UUID, audit log, index, partition, transaction lock, dan row-level/security policy.**
6. **Frontend harus dipisah berdasarkan role: admin, bendahara, kasir, kantin, kepala sekolah, orang tua, siswa.**
7. **Cybersecurity harus menjadi desain awal, bukan tambahan belakangan.**
